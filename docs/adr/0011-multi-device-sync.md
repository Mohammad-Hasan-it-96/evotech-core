# ADR 0011 — Multi-device sync for Fawateer (business-scoped device fleets)

- **Status:** Proposed
- **Date:** 2026-07-27 (revised 2026-07-28 and 2026-07-29, folding in the Fawateer app session's replies)
- **Deciders:** Founder/CTO, Platform architect
- **Supersedes / superseded by:** —
- **Related:** ADR 0010 (DeviceSubscriptions module), ADR 0008 (Download Center — private storage + short-lived signed URLs, reused for the bootstrap snapshot), ADR 0004 (product-to-platform API keys / Gateway), ADR 0003 (MySQL); `docs/ARCHITECTURE.md` §2 (module rules), §6.1 (Authentication), §7 (API contract), §10 (non-goals per feature); `docs/modules/DeviceSubscriptions.md`; `docs/api/fawateer-device-contract.md`. Originates from a contract request authored by the Fawateer Flutter app session; revised after that session's 2026-07-28 and 2026-07-29 replies (`docs/fawateer-replies/2026-07-28-fawateer-response.txt`, `docs/fawateer-replies/2026-07-29-fawateer-response.txt`).

## Context

Fawateer (فواتير) is an offline-first Arabic POS. Every device holds a **complete local SQLite (Drift) database** and works fully offline — that is the product's core promise. Today the platform serves Fawateer only its **licensing** contract through `Modules\DeviceSubscriptions`: `create_device`, `check_device`, `update_my_data`, `getPlans`, `add_review` — unversioned, unauthenticated, identified by `app_name` in the body, optionally namespaced at `/api/{slug}` (e.g. `/api/fawateer`). Fawateer 1.0.1 is in production in a real shop and must keep working unchanged.

The product owner now wants **multi-device**: one subscription = one **business** owning up to N **devices** that each sell independently, offline-capable, converging within ~30 s when online. Sold as tiers (1 / up to 3 / up to 5). This is the **first time shop business data (real financial records) reaches our server** — previously only opaque Google-Drive backup blobs left the device. Isolation between businesses is therefore the single most important security property of the feature.

Locked architecture decisions from the requesting session (not re-litigated here): substrate = evotech-core + MySQL (Firestore rejected); transport = plain HTTPS REST, poll + push, **no** websockets/Redis/queue for v1; latency = an FCM **data-only ping** ("something changed, pull now") reusing the already-wired, device-verified FCM channel; per-table merge rules (append-only union by UUID for ~90% of data, last-write-wins with tombstones for mutable rows, stock as an append-only movement log); two distinct clocks (a server sequence for the pull cursor, a device authorship logical clock for conflict resolution); mandatory idempotency keyed by client-generated UUID.

Four facts about evotech-core shape this ADR:

1. **There is no "business" entity.** In `device_subscriptions`, one row *is* one device *is* one subscription — the subscription fields (`is_verified`, `expires_at`, `plan_id`) live on the device row. "One subscription owns N devices" requires a **new owning aggregate**.
2. **The licensing shim is unauthenticated on purpose** — the module treats a `device_id` as non-secret (users copy it to WhatsApp support; `check_device` even masks `google_account` for this reason). That model is safe only because those endpoints expose nothing sensitive. It cannot carry financial data.
3. **Core has exactly two auth guards, and neither fits sync.** `auth:sanctum` is for humans/staff; `auth:product` (Gateway, ADR 0004) is one **shared key per product** — every Fawateer install would present the same key, so it cannot isolate businesses.
4. **The FCM sender is real and device-verified**, but `FirebasePushNotifier::send()` always emits a `notification` block (a user-visible tray banner) alongside `data.type`. A silent "doorbell" needs a data-only variant.

## Decision

**1. Introduce `device_businesses` as a new, module-local aggregate — the subscription owner.**
A business owns the subscription (`plan_id`, `expires_at`, `trial_expires_at`, `is_verified`), a `device_allowance` integer (default 1), and a per-business monotonic `last_seq`. It is **not** the platform tenant (`Companies` / `BelongsToCompany`, which is staff-side and login-based) and it is **not** a device row. Consumer shops stay non-tenant per ADR 0010; `device_businesses` is itself the scoping key for all sync data.

**2. Keep everything additive; 1.0.1 stays byte-identical.**
`device_subscriptions` gains a **nullable `business_id`**. When null (every install today, including Fawateer 1.0.1), the device row carries its own subscription exactly as now and `check_device` is unchanged. When set, the **business** row is the authoritative source of subscription state and seat allowance for its member devices. `check_device` for an enrolled device reports the *business's* expiry/verified (same JSON shape, different source) — a member device may never have had its own trial.

**3. `device_allowance` is an integer; tiers are presets over it.**
Enforced at the **business** level, never per device (a device is disposable hardware; per-device entitlement locks out on every phone swap) and never per user (there are no user accounts). Seat count = live `COUNT` of non-revoked member rows. Re-cutting tiers later is a pricing change, never a migration.

**4. Sync is a new authenticated Profile-B surface — not an extension of the unauthenticated shim.**
The multi-device client does not exist yet, so there is **no** backward-compatibility pressure. Sync endpoints live under **`/api/v1/sync/*`** (the `/api/{app}` wildcard explicitly excludes `v\d`, so this is the safe home) and are authenticated by a **new per-device sync credential**: minted at enrollment, hashed at rest, revocable server-side — the same pattern as Gateway's product keys (ADR 0004), but keyed per *device* rather than per *product*. The authenticated token resolves `business_id` server-side; any `business`/`app_name` in the request body is **ignored for authorization**. This one rule is what enforces cross-business isolation.

**5a. Owner onboarding — how a business comes into being (addendum, 2026-07-29).**
The original decisions specified enrollment *by join token* and assumed an owner seat already existed to mint that token — but never said how the **first** device becomes the owner. Closing that gap: a licensed single device promotes itself with `POST /api/v1/sync/business`, authenticated by its **licensing identity** (`app_name` + `device_id`) — the only identity it holds before it has a sync seat, and the same anchor `check_device` already trusts. The server requires a **verified** subscription on that device (a business can only sit on top of a live licence; `SUBSCRIPTION_REQUIRED` otherwise), then idempotently creates the `device_businesses` row seeded from the device's own subscription (expiry, trial, plan, verification), sets `device_subscriptions.business_id` (Decision 1), and mints the owner seat — returning its durable sync token once. `device_allowance` comes from the **plan the subscription holds**: `device_plans.device_allowance` (a first-class, dashboard-provisioned column, default 1) resolved via `DevicePlan::allowanceFor()` with the same per-app/shared scoping the catalog uses. Two fallbacks remain only when a plan row cannot be resolved — the legacy `sync.plan_allowance` override map, then `default_allowance` = 1 (the single-device tier a trial or unpriced plan keeps). It shares Decision 5's `fallback_device_id` rejection. **Idempotent by design:** a device that already owns a business gets its owner token *rotated* (old one invalidated) rather than a duplicate business — so a reinstall or lost token self-recovers, and the non-revocable owner seat (R1) is never duplicated. This endpoint, not enrollment, is the true head of the dependency chain: without it there is no owner seat, no join token, and no member can join.

**5b. Seat display name — an owner-editable label on the registry (addendum, 2026-08-11).**
The device registry must let an owner answer one question — *which of these rows is the phone I want to remove?* — before revoking. With only `last_used_at` bucketed coarsely, two identical tills both "seen minutes ago" are indistinguishable, and revoking the wrong one strands a cashier. Closing that gap additively: `device_seats.name` VARCHAR(40) NULL. **Nullable and additive** — existing seats stay unnamed, the client renders a last-seen fallback, and nothing in the shipped legacy shim changes. A joining/onboarding device may **propose** a name (its phone model) on `POST /sync/enroll` and `POST /sync/business`; the **owner** edits it via `PATCH /api/v1/sync/devices/{seat}` (owner-only, same rule as revoke, but the owner seat *is* a valid target — an owner names its own till). The server is authoritative over the stored value: trimmed, capped at 40 **characters** (multibyte, so Arabic labels like "الكاشير" count as characters not bytes), blank → null; so a proposal may come back trimmed or truncated and the client renders the returned value. **Not unique** — two phones may honestly be "الكاشير". The name is returned on every seat in `GET /sync/devices` and in the `enroll`/`business` responses (so a fresh device learns whether its proposal survived without a second call). **An owner-set name is never clobbered** by a later re-enroll or re-onboard: a re-proposed model name only fills a still-blank slot, so the owner's `PATCH` always wins. Purely a display attribute — it touches no authorization, isolation, or merge decision.

**5. Enrollment is by single-use QR/join token.**
The owner device mints a short-TTL (minutes), single-use, business-bound join token. A new device posts `{join_token, device_id, fcm_token, app_version}` and receives its durable per-device sync token. Enrollment at allowance returns a distinct machine-readable `allowance_exceeded` (so the app shows "upgrade your plan", not a generic error), and **rejects the exact literal `fallback_device_id`** — the lowercase, unhashed value `DeviceIdentityService` returns on any non-Android/iOS platform and on a null/empty native id (e.g. iOS `identifierForVendor` before first unlock). Two devices that both fail to read a native id share that one identity exactly, so admitting it would cross-contaminate two shops' books; the rejection carries its own machine-readable code so the app shows something honest rather than a generic failure.

Revocation nulls the credential server-side and frees the seat immediately — hiding UI is not revocation, and a phone swap must never consume an extra seat. **Revocation also stops the device selling, not only syncing.** The POS gates on a licence cached in `SharedPreferences` and enforces expiry locally so it keeps working offline; a device that only had its sync seat freed would keep taking unsynced, invisible sales until its cached expiry passed — useless for the motivating "a staff member left with the tablet" case. So a revoked seat makes `check_device` report **NOT verified** (same JSON shape as the business-expiry path in §2), and the next successful `check_device` locks it, bounded by the existing 7-day offline grace. A revoked seat is thereby **fully deactivated, not downgraded to a standalone subscription** — a seat device has no subscription of its own; the business owns it. This is the **one** place the sync credential and the licensing credential are deliberately coupled; everywhere else they stay independent.

Two bounds on revocation: **(R1) the owner seat is not revocable** — refused at the endpoint, not merely hidden in the UI, because revoking it orphans the business (a live subscription with no device able to mint join tokens, and no path back but operator intervention). **(R2) Revocation does not repossess data.** A revoked tablet keeps a complete local copy of the shop's books; we stop *future* selling (`check_device` NOT verified, bounded by the 7-day offline grace) and we stop it syncing, but nothing in this design can remote-wipe it — none could. Stated explicitly so the guarded-against failure is understood as non-technical: no one should later promise a shopkeeper a wipe capability the architecture does not have.

**6. Roles are deliberately flat in v1 — accountability, not permission.**
Every enrolled device is an equal peer for business data (any device may create/edit products including prices, sell, take payments, post stock). The server does **not** gate business writes by role. The only asymmetry is **ownership of the subscription** (structural, not a permission): the owner device issues/revokes join tokens, sees the conflict screen, and manages the plan/allowance. A `role` column (`owner`|`member`) and a single always-permit authorization hook on the write path are retained so a future restriction is a one-seam policy change — but no capability matrix, roles UI, or per-table rules are built now. `origin_device` is preserved faithfully through push and pull (never overwritten with the relaying device) — it is the audit trail that makes flat roles safe.

**7. Two physically distinct clocks.**
`device_changes.seq` — server-assigned, **per-business**, monotonic — drives the **pull cursor only**. `device_changes.authored_hlc` — a device-authored **HLC** travelling with the row — drives **conflict resolution only**.

The HLC is **stored as a string, not a number.** The client's implemented HLC (`lib/core/sync/hlc.dart`, 15 tests) packs to `<millis:15,0-pad>-<counter:5,0-pad>-<nodeId>` (e.g. `001785312000000-00003-a91f…c2`); the trailing node id is what gives two devices authoring in the same millisecond-and-counter a **deterministic** tie-break, so it cannot be folded into a BIGINT. The field widths are chosen so the packed form **sorts lexicographically in clock order** (a client test pins this), so `ORDER BY authored_hlc` / `WHERE authored_hlc > ?` are correct on a plain string column with default collation and the server never parses it.

**Node id = the first 16 hex characters of the device's SHA-256 id** (confirmed by the app session, 2026-07-29). So the packed HLC is `15 + 1 + 5 + 1 + 16 = 38` chars → **`authored_hlc VARCHAR(40)`**, and **`device_changes.origin_device VARCHAR(16)`** (the node id alone). The truncation is the app's decision to cap sync-metadata weight — `updated_at` + `origin_device` sit on every row of nine client tables, and full 64-hex width is ~2.8× the bytes, carried on the phone, in every Drive backup, and in every bootstrap snapshot transiting us. 64 bits only ever disambiguates *within one business* (≤5 devices, collision ~10⁻¹⁸), so it is ample. It is a **deterministic prefix**, so no mapping table: for an authenticated device we already hold the full `device_id`, and its node id is `SUBSTR(device_id, 1, 16)` — which is exactly what the no-echo filter (§9) compares `origin_device` against. Interaction to keep linked with Decision 5: `fallback_device_id` is not hex and truncates to `fallback_device_` *identically* for every device that hit the fallback, so §5's reject-at-enrol is what keeps the truncation scheme from cross-contaminating shops.

Device clocks are distrusted (Fawateer already has a 48 h licence-rollback guard; the client also clamps implausible drift at +1 h on receive). If the server clamps too, it **flags, it does not rewrite**: the stored `authored_hlc` stays exactly as authored (a separate boolean may record "clamp-suspect" for observability), because rewriting an authored value server-side would contradict the same-row "never overwrite authored data on relay" rule of §6 and — done half-way — would hand different devices different orderings, the one failure HLC exists to prevent.

**8. The per-business sequence is assigned under a row lock, in the change-insert transaction.**
On push, the business row's `last_seq` is incremented under a row lock (`SELECT ... FOR UPDATE` / atomic `UPDATE`) and stamped onto the change in the same transaction. This serializes sequence assignment **within a business**, so sequences are handed out in commit order and `pull WHERE seq > since ORDER BY seq` can never skip a row. A global auto-increment cursor is rejected: ids are assigned at statement time but rows become visible at commit time and commits do not finish in id order, so a puller can advance past a not-yet-committed lower id and never see it. The lock is per-business (2–5 devices, tens–hundreds of rows/day), so contention is nil and there is no cross-shop coupling — MySQL row locks are the right primitive; Redis is not needed (D2).

**9. Sync endpoints (shape, not final prescription), all `/api/v1`, business scope from the token:**
- `POST /api/v1/sync/business` — **owner onboarding** (see the 2026-07-29 addendum below); no sync auth, licensing identity → stands up the business + owner seat, returns the durable owner token. *(Implemented; the mint route below shipped as `POST /api/v1/sync/join-tokens`.)*
- `POST /api/v1/sync/enroll/token` — owner role → mint single-use join token. *(Shipped as `POST /api/v1/sync/join-tokens`; the mint response returns the raw `join_token` plaintext, its `expires_at`, and `business_uuid` — never the token record's uuid.)*
- `POST /api/v1/sync/join-tokens/{joinToken}/bootstrap` — owner role → attach the bootstrap snapshot + cursor `C` + SHA-256 to a token (multipart: file `snapshot`, `cursor`, `snapshot_sha256`). **`{joinToken}` binds on the RAW `join_token` plaintext (looked up by hash, scoped to the caller's business), not the record uuid** — the same identifier `/enroll` consumes, and the only one a client is ever handed. *(2026-08-16 fix: the route was implicit-model-bound on the uuid, which the mint never returns, so every client's URL 404'd; no HTTP test drove the route, so it went uncaught. Now unified on the plaintext, with an HTTP feature test. Cross-business or unknown token → 404, the isolation rule.)*
- `POST /api/v1/sync/enroll` — no auth, requires a valid join token → registers a seat, returns the durable sync token; `allowance_exceeded` at cap.
- `POST /api/v1/sync/push` — device token; per-row `accepted|rejected|conflict`; assigns per-business `seq`; **accepted even when the subscription is expired** (§10 below), returns `pending_count`; partial success is normal. Idempotency is **per row, not per batch**: `idempotency_key = row_uuid + authored_hlc`, enforced by `unique(business_id, idempotency_key)`. A batch-level key would make retry-after-partial-success incoherent (the batch key is already consumed, so the retry no-ops and the rejected rows are lost); a per-row key means the same edit re-pushed is byte-identical and no-ops, while a *later* edit to the same row carries a new HLC and is correctly a new change.
- `GET /api/v1/sync/pull?since=<seq>&limit=<n>` — device token; the business's changes, `seq` ascending, + `next_cursor` + `has_more`. Pull **does not echo the caller's own changes back** (filtered by `origin_device` server-side): the push response's per-row `accepted` is already the durability ack, so echoing is pure bandwidth waste, and with HLC last-write-wins the client would reject a stale echo of a row it has since edited locally anyway. **`next_cursor` is the highest seq *examined*, never the highest seq *returned*** — a scan watermark. This is load-bearing under no-echo: a page whose rows all belong to the caller filters to empty, and a returned-only cursor would not advance, so the client re-requests the same window forever (and `has_more` cannot rescue it — the client has no other way to learn the window was non-empty before filtering). It is also what lets the owner's `pull-to-current` in §13 advance its cursor **past its own pushed rows**, which it never receives back. A cursor older than retention returns a distinct `cursor_too_old` (§14), never an empty page — "nothing changed" and "you fell off the log" must not look identical.
- `GET /api/v1/sync/conflicts` and `POST /api/v1/sync/conflicts/{uuid}/resolve` — owner role only. *(**Descoped, 2026-08-11 — never built.** LWW (Decision 11) resolves every conflict deterministically server-side, so these were forensic, not corrective. The client surfaces a conflict **count** taken from the push response — a conflicted row still landed, so it never holds back the push watermark — and there is no resolution flow, by design. Any future forensics is a new, additive, cursored endpoint with its own pinned shape, never a reinterpretation of this one.)*
- `GET /api/v1/sync/devices` — any seat: registry list in `data`, each seat carrying its `name` (see the seat-name addendum below), with `meta.device_allowance` and `meta.seats_used` (active-seat count) so a client shows "N of M phones used" from the server, not a value cached at enrollment. `PATCH /api/v1/sync/devices/{uuid}` — owner-only: set a seat's display name (the owner seat included). `DELETE /api/v1/sync/devices/{uuid}` — owner-only: revoke (the owner seat refused, R1).

**10. Expiry locks selling, never the push of already-recorded changes.**
Authentication (valid, non-revoked device token) and subscription-active (`isActive()` on the business) are separate checks. `/sync/push` authenticates on the token and accepts writes **regardless** of subscription state, returning a pending count — an expired device may hold offline sales that must never be stranded on a phone the shopkeeper can no longer open. Only *new selling* is gated. This is why the sync credential is durable across expiry.

**11. Server-side conflict arbitration for three cases, requiring minimal materialization.**
*(Client surface descoped, 2026-08-11: the `/sync/conflicts` list/resolve endpoints (§9) were never built and the owner "conflict screen" below is not shipped. Arbitration itself stands — the claim-table guarantee (C1) and last-write-wins (C3) still run server-side and are authoritative — but conflicts are surfaced to the owner only as a **count** taken from the push response, with no resolution flow. The materialization below is what arbitration needs, not a forensic store the client reads.)* Most data is append-only union (no conflict). Three cases surface on a single screen on the **owner** device:
- **C1 serialized-unit double-sale** — a `sync_product_units` claim table with `unique(business_id, unit_id)` makes first-claim-wins a DB-level guarantee; later claims are rejected and raise a conflict. No reservation/lease (physical possession is already a natural mutex).
- **C2 duplicate product name** — detected across origin devices; never auto-merged (rows may differ in price/cost/barcode and may already have sales attached, so any merge re-points `sales_items.productId`, never deletes history).
- **C3 concurrent edit of a mutable row** — last-write-wins on the authorship clock, field-level where cheap (`shop_settings` is a single `id='default'` row that always collides — field-level LWW there); the losing value is retained in the conflict record.

This means the server **materializes only the tables it must arbitrate** (`sync_product_units`, enough of `sync_products`) and treats pure append-only financial tables (invoices, ledger, cashbox) as **opaque change-log blobs it never parses**. Relay + uniqueness/claim arbitration is not the server-side business logic §10 (non-goals) forbids: totals, profit, and balances are never recomputed server-side.

**12. The FCM ping is a data-only doorbell.**
`DevicePushNotifier` gains a data-only send (no `notification` block, `data:{type:'sync'}`, `android.priority=high`) reusing the existing per-app project/token machinery. After a push commits, one debounced ping is sent to each *other* active device in the business (never the author). It carries no business data. Dead-token pruning on FCM `UNREGISTERED` — a deferred follow-up under ADR 0010 — becomes a requirement here, because pings are frequent.

**13. A newly enrolled device is seeded from a snapshot, then pulls from the snapshot's seq — it is never replayed from `seq=0`.**
`device_changes` holds only changes recorded *after* sync began. A second device enrolling into an existing shop and pulling from `seq=0` would receive an empty history — no products, no customers, no prior invoices — so the seat comes up blank while every endpoint returns success. Replaying the owner's whole database into the oplog is rejected: a year-old shop is tens of thousands of rows, minutes of transfer, huge write amplification, and it pollutes the log with rows that were never changes. Instead:

1. Owner requests a join token (§5).
2. Owner does a **full `push` and full `pull`**, then reads **its own local pull cursor `C`** *before* starting the VACUUM, then snapshots via the client's existing `BackupEngine.createSnapshot()` (`VACUUM INTO` → a transactionally-consistent single-file copy, no WAL sidecar), then uploads the snapshot bound to the join token **and reports `C`**. Order: `push-all → pull-to-current → read C → VACUUM → upload(+C)`.

   **The cursor is the owner's own, not a server-side `last_seq` — this is the load-bearing correction (2026-07-29).** The owner's local cursor means precisely "everything at or below this is *applied to my database*," so everything `≤ C` is in the snapshot by construction and everything `> C` the joining device pulls; there is no window in which a row is neither. A server-side `last_seq` is wrong at every point in the sequence, because the server does not know which changes the owner has *applied*: if a second device pushed a change the owner has not yet pulled (e.g. server at seq 101, owner's cursor at 100), that row is in neither the owner's DB nor the snapshot, and a server-`last_seq` cursor would report past it — losing it permanently and silently. Push-all alone (the earlier "flush the queue" fix) closes only the owner's *unpushed* edits; sourcing the cursor from the owner closes the *unpulled remote edits* direction too. Read `C` **before** the VACUUM: if the owner applies a pull while the vacuum runs, a cursor read afterward could sit above content the snapshot lacks, reintroducing the loss; reading before only ever errs toward "snapshot has slightly more than `C` covers," which the joiner absorbs by re-pulling a few rows dedup already handles.
3. Joining device downloads the snapshot, **verifies its SHA-256 before touching its live DB** (against the hash carried in the enrolment QR — see H2 below — so the check is end-to-end owner→joiner, not merely transit-integrity), restores (the client's `restore()` already enforces a schema-downgrade refusal, the integrity check, and a rollback-safe swap), then pulls from `C`.
4. The joining device stamps its **own** node id on everything it authors from then on; the owner's `origin_device` values inside the snapshot are preserved unchanged (same rule as §6's never-overwrite-on-relay). Licence state lives in `SharedPreferences`, not the Drift DB, so restoring the owner's snapshot cannot transplant the owner's subscription onto the joining device.

**Snapshot custody is transient, and we reuse the Download Center's private delivery (ADR 0008), not a new mechanism.** The **owner** uploads the snapshot through the API to a **private disk** (never web-served); the server returns a **short-lived signed URL** bound to the single-use join token, deletes the file **on consumption or at the join token's TTL** (minutes), whichever is first. The snapshot is a shop's entire *unencrypted* financial history in one file (the backup feature ships it to Drive with no client-side encryption), so there is a hard non-goal: **we never retain it as a "latest backup" convenience.** Being a transient courier is a far smaller data-custody commitment than becoming the permanent home of every shop's books. A zero-storage alternative — when both devices sign into the same Google account, the joiner restores from the owner's existing Drive backup and skips our server entirely — is kept as an offer for the common single-owner-two-devices case, but not as the primary path, since a staff device may legitimately not share the owner's Google account.

**Two cheap hardenings on the handshake (2026-07-29).** **(H1) Upload requires the owner's authenticated *device token*, with the join token as the binding, not the credential.** The join token is rendered on-screen as a QR; if it alone authorised the upload, anyone who photographed it could race the joiner and upload a *poisoned* snapshot that the joiner then restores as its whole database. Enrol (the joiner obtaining its sync token) stays join-token-authenticated; upload (an owner action) is a distinct, owner-token-authenticated endpoint — the two must not be conflated. **(H2) The expected SHA-256 travels in the enrolment QR**, computed by the owner locally (it made the file) and checked by the joiner against the server-delivered bytes — so integrity is genuinely owner→joiner and never trusts the server's stored hash, which only certifies transit. Ordering constraint: the QR is rendered **after** the upload, since the hash does not exist until the snapshot does (the natural implementation order is the opposite, hence worth stating).

**14. `device_changes` retention is bounded, and falling off the log re-uses the §13 bootstrap.**
The oplog is append-only and would otherwise grow unbounded (a busy shop writes on the order of a thousand rows/day — invoice + lines + a cashbox/ledger entry + a stock movement per line — six figures a year, most never read again after first pull). A retention cutoff means a device offline longer than the window cannot catch up incrementally; the correct recovery is to **re-bootstrap it via §13**, not to invent a second path. This is why §13 and §14 are decided together: bootstrap is not an enrollment special case, it is the general "your cursor is older than history" recovery. `pull` signals this with the distinct `cursor_too_old` of §9 so the client re-seeds instead of concluding nothing changed. **(Implemented 2026-07-29, after the first PR:** a per-business `pruned_through_seq` watermark on `device_businesses`; a daily `device-subscriptions:prune-sync-changes` command (config `sync.retention_days`, default 60) deletes each business's changes at or below the highest too-old `seq`, keeping the retained set contiguous; `pull` throws `cursor_too_old` when `cursor < pruned_through_seq`. The watermark only ever advances.)

## Consequences

**Positive**
- Multi-device converges on the existing platform + MySQL with no new infrastructure (no websockets/Redis/queue), matching the shop scale (2–5 devices, tens–hundreds of rows/day).
- Cross-business isolation is enforced at one seam (business scope derived from an authenticated per-device token), which is the feature's paramount security property.
- Fully additive: the shipped licensing contract (`create_device`/`check_device`/`update_my_data`/`getPlans`/`add_review`) is untouched, so Fawateer 1.0.1 keeps working.
- Expired businesses can still upload stranded offline sales — an expired subscription can never destroy a shop's books.
- The FCM channel is already implemented and device-verified; only a data-only variant is added.

**Negative / trade-offs**
- A **third authentication mechanism** (per-device sync token) joins `auth:sanctum` and `auth:product`. Justified because neither existing guard can isolate businesses; mitigated by copying Gateway's proven hashed/revocable design.
- The subscription's authoritative location becomes conditional (`business_id` null → device row; set → business row). The rule is explicit but is a second thing to hold in mind; the module doc will draw it.
- The server now stores some real business data (change log + arbitration tables) — a genuine change in data-custody responsibility, called out in Context and bounded to what conflict arbitration requires. Enrollment adds a **transient** custody of the whole unencrypted DB (the bootstrap snapshot, §13) — the sharpest data-custody exposure in the feature — deliberately capped to a single-use, minutes-TTL, delete-on-consumption file on a private disk, never retained.
- Flat roles mean concurrent edits to the same product (including price) are a normal path, not an edge case — the C3/offline-stale-edit path needs real tests, not smoke tests.
- Bootstrap and retention (§13/§14) are one mechanism, so enrollment cannot be designed in isolation: `/sync/enroll` must return (or trigger) the snapshot-seed handshake, and the same path is the fall-off-the-log recovery.
- The bootstrap test **must** be a *third* device enrolling while a *second* device has an unpulled change outstanding — not the happy path. The happy-path enrol-then-pull test passes under both the broken (server-`last_seq`) and the correct (owner-cursor) rule, so it cannot protect the §13 correction; only the unpulled-outstanding case distinguishes them.

**Deferred (additive, no contract change)**
- `device_changes` retention/compaction (§14) — decided now, built after the first PR; the `cursor_too_old` sentinel and the §13 re-seed path are in from the start so retention needs no contract change when it lands.
- Retiring the legacy licensing shim once a versioned+authenticated app ships (already deferred under ADR 0010).
- Any role-based restriction, should a larger shop ever ask — a policy change at the retained authorization hook, not a re-architecture.
- Per-business FCM topic fan-out (publish once) instead of per-device sends, if device counts per business ever grow beyond the tiers.

## Amendment to the constitution

None. Sync is added as a **versioned, authenticated `/api/v1` surface**, so it needs no exception to §7 (unlike ADR 0010's shim). The per-device sync token is a new credential type consistent with §6.1's principle of layering authentication by audience. §10 (per-feature non-goals) is honored: no server-side recomputation of business figures; the server relays and arbitrates uniqueness only.
