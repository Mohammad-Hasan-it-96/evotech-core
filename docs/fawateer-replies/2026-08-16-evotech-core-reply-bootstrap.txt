--------------------------------------------------------------------------------
THE BUG, IN ONE LINE
--------------------------------------------------------------------------------
The upload route was resolving {token} as the join-token RECORD's internal uuid.
We never give you that uuid. The mint response returns the raw `join_token`
string, its `expires_at`, and `business_uuid` — and nothing else. So no client
could ever build a URL that resolved. Every value 404'd, including the real token,
because the real token's plaintext is not its uuid.

It slipped through because every test we own attaches the snapshot by calling the
service in-process — none drove the actual HTTP route. So the route had zero HTTP
coverage. We have now added that test (it fails on the old code, passes on the
new).

--------------------------------------------------------------------------------
YOUR FOUR QUESTIONS
--------------------------------------------------------------------------------
1. Implemented, or a skeleton?
   IMPLEMENTED and working. It writes cursor + snapshot path + sha256 to the token
   and the joiner gets a real signed snapshot URL. The 404 was the routing bug
   above, not a missing controller.

2. What does {token} bind on?
   AFTER THE FIX: the raw `join_token` string — the exact value POST

   We look it up by hash, scoped to your business. No uuid, no hash, no other

3. The multipart field names.
   File field:  snapshot          (you had this right)
   Also required:
       cursor            integer, >= 0
       snapshot_sha256   64-hex string   <-- you sent `sha256`; rename it

4. Order — upload BEFORE the QR, or after redeem?
   BEFORE, exactly as you assumed (ADR 0011 Decision 13). The joiner only gets a

   Your ordering is correct; keep it.

--------------------------------------------------------------------------------
ONE MORE THING — THE DOWNLOAD URL, SO YOU DO NOT REBUILD IT
--------------------------------------------------------------------------------
You noticed GET /api/v1/sync/bootstrap/{token} also 404s for a fresh token. Two
reasons, both fine:
  - there is no snapshot yet for a just-minted token, and
  - you should never CONSTRUCT that download URL yourself.
The joiner receives the full, signed download URL ready-made in the enroll
response, at `data.bootstrap.snapshot_url`. Follow that string as-is (it carries
its own signature and expiry). Do not append the token to /sync/bootstrap/ by
hand — that path binds differently (it is the server's own signed link) and will
not match. `snapshot_url` is present only when a snapshot was attached; when it is
null there is nothing to download and cursor `C` alone is the handoff.

--------------------------------------------------------------------------------
THE CORRECT CALL
--------------------------------------------------------------------------------
    # 1. owner mints (you already do this)
    POST /api/v1/sync/join-tokens          -> data.join_token = "evojoin_...."

    # 2. owner uploads the snapshot AGAINST THAT RAW STRING
    curl -X POST \
      -H "Authorization: Bearer <owner seat token>" \
      -H "Accept: application/json" \
      -F "snapshot=@shop.sqlite" \
      -F "cursor=1" \
      -F "snapshot_sha256=<64-hex>" \
      https://api.evotech-sys.com/api/v1/sync/join-tokens/evojoin_..../bootstrap
    # -> 200 {"data":{"join_token_uuid":"...","cursor":1}}

    # 3. owner shows the QR of data.join_token

    # 4. joiner redeems -> gets data.bootstrap.snapshot_url (signed, ready to GET)
    POST /api/v1/sync/enroll  { "join_token": "evojoin_....", "device_id": "..." }
