--------------------------------------------------------------------------------
#1 — GET /sync/conflicts: PIN THE SHAPE, OR REMOVE IT FROM THE CONTRACT
--------------------------------------------------------------------------------
The client parses `conflicts` out of the push response (it must — a conflicted
row still LANDED, so it cannot be allowed to stall the push watermark), and it
now surfaces the COUNT on the sync screen. It cannot do more than that.

`GET /sync/conflicts` is referenced in the contract but:
  - it is not in `modules/DeviceSubscriptions/Routes/api.php`, and
  - its response shape was never pinned in the 07-27 → 07-29 exchange.

We do not want to build a client screen against a shape we invented. So please
decide one of:

  (a) IMPLEMENT IT. Then we need the response pinned: what identifies a
      conflicted row (table + row uuid + authored_hlc?), what the server kept
      versus rejected, and whether the endpoint is paginated/cursored like
      /changes. Say explicitly whether a conflict is a durable record or a
      transient log entry that retention prunes.

  (b) REMOVE IT from the contract. We will keep showing the count and document
      the absence of a resolution flow as a deliberate gap.

Our honest lean is (b) FOR NOW. We have no resolution UI and no design for one,
and a count the owner can see is what keeps this a KNOWN gap rather than an
invisible one. LWW already resolves every conflict deterministically; the
endpoint would be for forensics, not for correctness. If you agree, we would
rather you spend the effort on #2, which a shop hits on day one.

--------------------------------------------------------------------------------
#2 — DEVICE NAME ON THE SEAT (small, additive, high value)
--------------------------------------------------------------------------------
`device_seats` has: uuid, device_business_id, app_name, device_id, node_id,
role, prefix, token_hash, push_token, last_used_at, revoked_at, timestamps.

There is NO owner-assigned name, and this is a real usability hole we cannot
fix on the client. The device registry screen ("الأجهزة والمزامنة") has to let
an owner answer ONE question: *which of these rows is the phone I want to
remove?* Today the only discriminators are:

  - `isCurrent` (matched on the seat uuid this device holds), and
  - `last_seen_at`, bucketed coarsely into now / minutes / hours / days.

For a two-phone shop that is survivable. For a three- or five-seat shop it is
not: two identical Samsung tills, both "seen minutes ago", and revoking the
wrong one strands a cashier mid-shift. There is nothing else on the row.

REQUEST — a nullable, owner-editable label:

  - `device_seats.name` VARCHAR(40) NULL.
  - Accepted optionally on `POST /sync/enroll` and `POST /sync/business`
    (the joining device can propose one, e.g. the phone model).
  - Editable by the OWNER seat only: `PATCH /api/v1/sync/devices/{seat}`
    with `{ "name": "..." }`. Owner-only, same rule as revoke.
  - Returned in `GET /sync/devices` on every seat.
  - Trim, cap at 40 chars, allow Arabic. Not unique — two phones may honestly
    be called "الكاشير".

Nullable is important: existing seats must keep working with no name, and the
client already renders a sensible fallback. We will treat null as "unnamed" and
keep showing last-seen underneath.

If you would rather not add a PATCH route, accepting the name on enroll alone is
already most of the value — say so and we will take that.

--------------------------------------------------------------------------------
NOT AN ASK — a client bug we found, recorded so you know we know
--------------------------------------------------------------------------------
`CURSOR_TOO_OLD` is NOT handled by the client. `SyncError.fromCode` maps
SUBSCRIPTION_REQUIRED, ALLOWANCE_EXCEEDED, INVALID_JOIN_TOKEN,
FALLBACK_DEVICE_REJECTED, DEVICE_REVOKED, OWNER_ONLY and
OWNER_SEAT_NOT_REVOCABLE — everything else, including CURSOR_TOO_OLD, falls to
`SyncError.server`, which the scheduler treats as retryable.

So a device that falls behind your retention window would retry forever and
never converge, silently, while the UI reports an ordinary server error. That is
ours to fix (the device must re-bootstrap from a fresh snapshot), and it is on
our list before the field test. We only need (3c) — the real retention window —
to decide how aggressively to test it.
