--------------------------------------------------------------------------------
§1 — THE BOOTSTRAP CURSOR RULE IS STILL WRONG. OUR ERROR, PROPAGATED.
--------------------------------------------------------------------------------
Our §B step 2 said "take the seq AFTER the VACUUM completes." You recorded it in
the ADR verbatim as correct. It is not, and your P2 does not close it.

P2 fixes one direction and it was a good catch: the owner's own OFFLINE EDITS,
present in the snapshot but not yet in the log. `push-all -> VACUUM` does fix
that. The opposite direction is still open, and it loses data silently.

  FAILING CASE (needs only two existing devices — i.e. every 3- and 5-seat tier):

    Business has owner O and member M. Server log at seq 100. O's local pull
    cursor is 100. M pushes a change -> seq 101. O has not pulled it.

    O now enrols device N, following the agreed order:
      push-all        -> O's pending rows get seqs 102, 103
      VACUUM INTO     -> snapshot of O's DB
      read last_seq   -> 103
      report C = 103

    Is seq 101 in the snapshot? NO. push-all does not PULL, so O never applied
    M's change; it is in neither O's database nor therefore the snapshot.

    N restores the snapshot and pulls from 103. It never sees 101.
    Permanently lost, no error, no retry, nothing to observe.

  THE FIX: THE OWNER REPORTS ITS OWN LOCAL PULL CURSOR, READ IMMEDIATELY BEFORE
  THE VACUUM, AFTER A FULL PUSH **AND** PULL. Not a fresh server-side last_seq.

    push-all  ->  pull-to-current  ->  read O's OWN cursor C  ->  VACUUM INTO
              ->  upload snapshot (+C)

  Why this is correct BY CONSTRUCTION rather than by ordering luck: the owner's
  cursor means precisely "everything at or below this is applied to my
  database." So everything <= C is in the snapshot by definition, and everything
  > C is pulled by the joining device. There is no window in which a row can be
  neither.

  Two ordering details that matter:

    - READ THE CURSOR BEFORE THE VACUUM, not after. If the owner applies a pull
      while the vacuum is running, a cursor read afterwards would sit above
      content the snapshot does not contain — reintroducing the same loss.
      Reading before is safe in the harmless direction: the snapshot may contain
      slightly MORE than C covers, and the joining device merely re-pulls a few
      rows it already has, which dedup handles.

    - ASK THE OWNER, NOT THE SERVER. A server-side last_seq read cannot be
      correct here at any point in the sequence, because the server does not
      know which changes the owner has APPLIED. That is the whole error: we
      were sourcing the cursor from the party that does not hold the answer.

  Please move the first-PR test from "enrol-from-snapshot-then-pull-from-seq" to
  the failing case above — a THIRD device enrolling while a second device has an
  unpulled change outstanding. The happy-path test passes under both the broken
  and the fixed rule, which is what makes this worth writing down.


--------------------------------------------------------------------------------
§2 — YOUR D2 (NO ECHO) NEEDS ONE PIN, OR pull CANNOT ADVANCE
--------------------------------------------------------------------------------
We agree with no-echo. But it introduces a requirement your endpoint spec does
not state (it says only "+ next_cursor + has_more"):

    next_cursor MUST be the highest seq EXAMINED, never the highest seq RETURNED.

Otherwise a page whose rows all belong to the caller is filtered to empty and
returns a cursor that has not moved — the client re-requests the same window
forever, and `has_more` cannot rescue it because the client has no other way to
learn the window was non-empty before filtering.

This is also load-bearing for §1: under no-echo, the owner's `pull-to-current`
must advance its cursor PAST ITS OWN PUSHED ROWS, which it never receives. Only
a scan-watermark cursor does that. So the two fixes are the same fix.

§3 — P1 ANSWERED: NODE ID IS 16 HEX CHARS. SIZE VARCHAR(40).
--------------------------------------------------------------------------------
Our device id is SHA-256 hex — 64 characters
(device_identity_service.dart:32). At full width the packed HLC is 86 chars, so
your VARCHAR(96) guess fits.

We are NOT going to use full width. Truncate the node id to the first 16 hex
characters of the existing device id:

    packed HLC   = 15 + 1 + 5 + 1 + 16  =  38 chars   ->  authored_hlc VARCHAR(40)
    origin_device                        =  16 chars   ->  VARCHAR(16)

  WHY, and it is not about your column: updated_at and origin_device sit on
  EVERY ROW OF NINE TABLES. Full width is ~150 bytes of sync metadata per row;
  truncated it is ~54. A shop writing on the order of 1,200 rows/day is the
  difference between roughly 66 MB and 24 MB per year — carried on a phone, in
  every Google Drive backup, and now in every bootstrap snapshot transiting your
  VPS. The 2.8x applies to your device_changes rows too, but the client is where
  it hurts.

  WHY 64 BITS IS AMPLE: node ids only ever need to disambiguate WITHIN ONE
  BUSINESS — at most 5 devices. Collision probability there is ~10^-18. Even
  across a million devices globally it is ~3x10^-8. There is no scenario in this
  product where 16 hex characters is the thing that fails.

  IT IS A DETERMINISTIC PREFIX, so you never need a mapping table: for the
  authenticated device you already hold the full device_id, and its node id is
  SUBSTR(device_id, 1, 16). That is what your no-echo filter should compare
  against.

  Caveat, and it is the same one behind your Decision 5: 'fallback_device_id' is
  not hex and truncates to 'fallback_device_' — which would be IDENTICAL for
  every device that hit the fallback. Rejecting it at enrol (already decided)
  is what keeps this safe; we are noting the interaction so the two decisions
  stay linked in the ADR rather than drifting apart.


--------------------------------------------------------------------------------
§4 — TWO HARDENING ITEMS ON THE BOOTSTRAP HANDSHAKE
--------------------------------------------------------------------------------

H1. THE SNAPSHOT UPLOAD SHOULD REQUIRE THE OWNER'S DEVICE TOKEN, NOT ONLY THE
    JOIN TOKEN. As specced, the join token alone authorises the upload — and
    that token is rendered on screen as a QR code. Someone who photographs it
    could race the joining device and upload a POISONED snapshot, which the
    joiner then restores as its entire database. Not a likely attack, but the
    fix is free: require the owner's authenticated device token for upload, with
    the join token as the binding rather than the credential.

H2. CARRY THE SHA-256 IN THE ENROLMENT QR. As designed, the server stores both
    the snapshot and its expected hash, so the integrity guard proves only that
    the file was not corrupted in transit — it is self-certified by the party
    holding the file. The QR is an out-of-band channel that already exists and
    already travels owner-screen -> joiner-camera. Putting the hash there makes
    the check genuinely end-to-end for nothing.

    Ordering constraint this imposes: the QR must be generated AFTER the upload,
    not before, because the hash does not exist until the snapshot does. Worth
    stating, since the natural implementation order is the opposite.


--------------------------------------------------------------------------------
§5 — TWO CLARIFICATIONS ON YOUR §3 REVOCATION NUANCE
--------------------------------------------------------------------------------
"Fully deactivated, not downgraded to a standalone subscription" is the right
reading and we agree. Two things to pin beside it:

R1. THE OWNER SEAT SHOULD NOT BE REVOCABLE. Revoking it would orphan the
    business: a live subscription with no device able to mint join tokens, and
    no path back except operator intervention. Refuse it at the endpoint rather
    than relying on the UI not to offer it.

R2. REVOCATION DOES NOT REPOSSESS DATA. The revoked tablet keeps a complete
    local copy of the shop's books. We stop future selling (check_device NOT
    verified, bounded by the 7-day offline grace) and we stop it syncing. We
    cannot remote-wipe it, and nothing in this design could. Please state that
    in the ADR explicitly — the failure mode we are guarding against is not
    technical, it is someone later promising a shopkeeper a capability the
    architecture does not have.
