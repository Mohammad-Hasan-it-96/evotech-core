--------------------------------------------------------------------------------
§A — ACCEPTED WITHOUT ARGUMENT
--------------------------------------------------------------------------------

A1. SYNC CANNOT RIDE THE UNAUTHENTICATED SHIM. You are right and our §5 was
    self-contradictory — it asked for an enrollment credential while still
    describing sync as "additive to the licensing shim."

    Your reasoning is stronger than you stated it. It is not merely that a
    device id happens to be guessable: the app RENDERS IT ON SCREEN with a
    copy-to-clipboard button (DeviceIdCard, on both the activation and
    subscription pages) precisely so users can send it to support over
    WhatsApp. And check_device already masks google_account for exactly this
    reason. A device id is not a weak secret; it is a published identifier.
    Scoping financial records by it would hand a shop's books to anyone who
    saw a support message.

    => Per-device hashed revocable token, Gateway pattern. Agreed. Treat this
       as the feature's foundation, not a wrapper around it.

A2. PER-BUSINESS SEQUENCE UNDER A ROW LOCK. Agreed, and the reasoning is the
    part we want on record in the ADR: ids are assigned at STATEMENT time but
    become visible at COMMIT time, so a global auto-increment cursor does not
    merely reorder rows — it PERMANENTLY SKIPS them. A puller that sees 100 and
    advances past an uncommitted 99 never returns for it. Silent, unrecoverable,
    and invisible in testing until two devices push concurrently.

A3. "BUSINESS" IS A NEW AGGREGATE, NOT Companies. Agreed, and for a reason
    worth adding: Companies presumes a human login. A Fawateer shop has none
    and will never have one — the whole licensing model is login-less by
    design. Nullable business_id keeping 1.0.1 byte-identical is the right
    call; that build is running a real shop today.

A4. MATERIALIZING product_units + products FOR ARBITRATION (your CONFLICT 6).
    Accepted as the intended reading of our §10. "No server-side business
    logic" meant: never recompute a total, a profit, or a balance. Uniqueness
    arbitration is not that.

    One reassurance on C2 (duplicate product names created offline on two
    devices): merging them is SAFE here, because sales_items snapshots
    productName, price, cost, saleType and the attribute bag at sale time. A
    historical invoice does not read through to the product row, so collapsing
    two product rows cannot alter any past receipt. That is a deliberate
    existing invariant ("reprint-eternal"), not a happy accident — you can rely
    on it.

A5. DATA-ONLY FCM VARIANT. Agreed, and thank you for the correction on
    FirebasePushNotifier — see §G3.

§B — THE GAP: THERE IS NO BOOTSTRAP PATH FOR A NEWLY ENROLLED DEVICE
--------------------------------------------------------------------------------
This is the one thing we would ask you to design before writing enrollment.

device_changes only holds changes recorded AFTER sync begins. A second device
enrolling into an existing shop pulls from seq=0 and receives an empty history:
no products, no customers, no prior invoices, no debts. Every device after the
first comes up blank. The seat is created, the credential works, pull returns
200 OK — and the shop sees an empty till.

Replaying the owner's whole database into the oplog is the obvious fix and a
bad one. A shop a year in holds tens of thousands of rows; pushing them
row-by-row as JSON to seed one tablet is minutes of transfer, a huge oplog
write amplification, and it pollutes the change log with rows that were never
changes.

RECOMMENDATION: SEED FROM A SNAPSHOT, THEN PULL FROM THE SEQ AT SNAPSHOT TIME.

We already have this machinery in production, device-verified:

  BackupEngine.createSnapshot()  (lib/features/backup/data/backup_engine.dart)
    - `VACUUM INTO` produces a transactionally-consistent single-file copy of
      the whole DB while it is open. No WAL sidecar handling needed.
    - It is deliberately provider-agnostic — it "knows nothing about Google
      Drive." It can feed an upload to your VPS with no change.
    - It already emits a BackupManifest carrying schemaVersion, appVersion,
      createdAt, deviceId, and a hex SHA-256 of the bytes.

  BackupRepositoryImpl.restore() already enforces three guards we want here
  verbatim: a schema DOWNGRADE refusal (a newer snapshot into an older build
  corrupts silently, because Drift migrations are forward-only), a SHA-256
  integrity check performed BEFORE the live DB is touched, and a rollback-safe
  swap. Restore is a path a real shop has already exercised.

Proposed flow:

  1. Owner requests a join token (your POST /api/v1/sync/enroll/token).
  2. Owner device uploads a fresh snapshot, bound to that join token, and
     reports the business's current last_seq as observed at snapshot time.
     Take the seq AFTER the VACUUM completes — seeding slightly stale and
     re-pulling a few changes is harmless; seeding ahead loses rows forever.
  3. Joining device enrolls, downloads the snapshot, verifies the SHA-256,
     restores, then pulls from that seq.
  4. Server deletes the snapshot on consumption or at the join token's TTL.

Four notes on this, all load-bearing:

  B1. THE SNAPSHOT MUST BE SHORT-LIVED ON YOUR SIDE. It is the shop's entire
      unencrypted financial history in one file (the backup feature ships it
      to Drive as-is, protected only by the user's Google account — there is no
      client-side encryption today). Bind it to the single-use join token,
      delete on consumption, hard TTL in minutes. Do not retain it as a
      "latest backup" convenience; that would quietly make your VPS a
      permanent custodian of every shop's books, which is a much larger
      commitment than sync.

  B2. THE JOINING DEVICE MUST NOT INHERIT THE OWNER'S NODE IDENTITY. The
      snapshot carries the owner's rows including origin_device values. Those
      stay as they are — they are the audit trail, and preserving them is the
      same rule as your "never overwrite origin_device_id on relay." But the
      joining device stamps its OWN node id on everything it authors from then
      on. We handle this client-side; flagging it so the contract is explicit.

  B3. LICENSING IS UNAFFECTED BY THE RESTORE. License state lives in
      SharedPreferences, not in the Drift database, so restoring the owner's
      snapshot cannot transplant the owner's subscription onto the joining
      device. That is a genuine safety property of the existing split, and it
      means enrollment and licensing stay cleanly separable.

  B4. A ZERO-STORAGE ALTERNATIVE EXISTS WHEN THE GOOGLE ACCOUNTS MATCH. If both
      devices sign into the same Google account, the joining device can restore
      from the owner's existing Drive backup and skip your server entirely. We
      do NOT propose this as the primary path — a staff device may legitimately
      not share the owner's Google account, and requiring it would make
      enrollment fail for the exact staffing case this feature is for. Worth
      keeping as an offer for the single-owner-two-devices case, which we
      expect is the common one.

§C — RETENTION ON device_changes (FOLLOWS DIRECTLY FROM §B)
--------------------------------------------------------------------------------
The oplog is append-only and unbounded. A busy shop writes on the order of a
thousand rows a day (a sale is an invoice plus its lines, plus a cashbox or
ledger entry, plus a stock movement per line). That is six figures a year per
business, most of it never read again after the first pull.

Once there is a retention cutoff, a device offline longer than the window
cannot catch up incrementally. The correct response is to re-bootstrap it —
the SAME mechanism as §B. That is the argument for designing them together:
bootstrap is not a one-time enrollment special case, it is the general
fallback for "your cursor is older than history."

Suggested: pull returns a distinct machine-readable `cursor_too_old` rather
than an empty page, so the client knows to re-seed instead of concluding
nothing changed. An empty page and "you have fallen off the log" must not look
identical — that is the same class of bug as the skipped-seq problem in A2.


--------------------------------------------------------------------------------
§D — REVOCATION MUST LOCK THE DEVICE, NOT ONLY FREE THE SEAT
--------------------------------------------------------------------------------
Your revoke sets revoked_at and nulls sync_token_hash. That correctly stops the
device syncing and frees the seat instantly. But it does not stop it SELLING.

The app's gate runs off the license cached in SharedPreferences and enforces
expiry LOCALLY from that cached expires_at, specifically so the POS keeps
working offline. A revoked device therefore keeps taking sales — offline,
unsynced, invisible — until its cached expiry date passes. If the motivating
scenario is "a staff member left and did not give the tablet back," revoke as
specified does not address it.

=> For a device with revoked_at set, check_device must report NOT verified
   (same JSON shape, as with the business-expiry change you already flagged in
   CONFLICT 5). Then the next successful check locks it, and the existing
   7-day offline grace bounds the worst case — which is exactly the revocation-
   latency bound that grace window was designed to express.

   Note this is the one place where the sync credential and the licensing
   credential must NOT be independent. Everywhere else your separation (§8) is
   right and we agree with it.


--------------------------------------------------------------------------------
§E — INTEROP MISMATCH: authored_hlc MUST BE VARCHAR, NOT BIGINT
--------------------------------------------------------------------------------
Settle this before you write the migration.

Our HLC is implemented and tested (lib/core/sync/hlc.dart, 15 tests). It packs
to TEXT:

    <millis, 15 digits, zero-padded>-<counter, 5 digits, zero-padded>-<nodeId>
    e.g.  001785312000000-00003-a91f...c2

The node id is not decoration — it is what gives two devices a DETERMINISTIC
tie-break when they author in the same millisecond with the same counter.
Without it, concurrent edits have no total order and C3 (last-writer-wins) is
undefined at exactly the moment it matters. It does not fit in a BIGINT.

=> Make it VARCHAR(64).

The field widths were chosen so the packed form SORTS LEXICOGRAPHICALLY IN
CLOCK ORDER (there is a test pinning this). So `ORDER BY authored_hlc` and
`WHERE authored_hlc > ?` are correct on a plain string column with no special
collation and no parsing server-side. You get the ordering for free; you never
need to decompose it.

E1. ONE DECISION FOR YOU, on clamping. We agree with clamping implausible
    values rather than rejecting them — rejecting means discarding a real sale
    because a phone's clock is wrong, which is data loss to protect ordering,
    the wrong trade for a POS. We clamp client-side on receive at +1h drift.

    If you ALSO clamp server-side, decide explicitly whether you REWRITE the
    stored value or merely FLAG it:
      - Rewriting makes the clamped value canonical, so every device sees the
        same ordering. Cleaner outcome.
      - But it contradicts your own "preserve origin_device_id, never overwrite
        on relay" principle, applied to the same row.
    Either is defensible. Pick one and put it in the ADR, because a
    half-and-half implementation gives different devices different orderings,
    which is the one failure mode HLC exists to prevent.


--------------------------------------------------------------------------------
§F — THREE SMALLER PINS
--------------------------------------------------------------------------------

F1. THE FALLBACK ID LITERAL IS LOWERCASE. Your rejection rule is right and more
    important than it looks, but pin the exact string. DeviceIdentityService
    returns the literal:

        'fallback_device_id'

    (lib/features/licensing/data/services/device_identity_service.dart:39)

    It is returned unhashed and unsalted on any non-Android/iOS platform, and
    on a null/empty native id — e.g. iOS identifierForVendor before first
    unlock. Two devices that both fail to read a native id share one identity
    exactly, so admitting it would silently cross-contaminate two shops'
    financial data. Reject at enroll with a distinct machine-readable code so
    the app can show something honest rather than a generic failure.

F2. idempotency_key IS PER ROW, NOT PER BATCH. Your endpoint spec says partial
    success is normal ("per-row accepted|rejected|conflict"), which is right —
    but a batch-level key then makes retry-after-partial-success incoherent:
    the batch key is already consumed, so the whole retry no-ops and the
    rejected rows are lost.

    Suggest: idempotency_key = row_uuid + authored_hlc. The same edit re-pushed
    is byte-identical and no-ops; a LATER edit to the same row has a different
    HLC and is correctly a new change. UNIQUE(business_id, idempotency_key)
    then gives D6 for free exactly as you described.

F3. DOES pull ECHO THE CALLER'S OWN CHANGES BACK? Not specified. We are fine
    either way and will filter client-side on origin_device regardless (we must
    anyway — a row we authored may have been edited locally since we pushed it,
    and re-applying the older payload would clobber a newer local edit). Worth
    one line in the ADR so it is a decision rather than an accident. Mild
    preference for echoing: it doubles as a durability acknowledgement.
